## 注入修正（registry.yaml，仅数据）

**根因**：模板 `workflows/ltx-2.3-i2v.json` 是两段式管线：
`320.290` 重排首帧到目标 WxH → `320.292/320.294`（`a/2`）→ `320.295` 半分辨率生成 → `320.287 LTXVLatentUpsampler`（×2 上采样器 `ltx-2.3-spatial-upscaler-x2-1.1`）→ 全分辨率精修出片。
原 registry 把 `width/height` 同时注入 `320.290`（图像重排）和 `320.295`（一段 latent），**字面量覆盖了 `a/2` 链接**，两段都在目标分辨率，经 ×2 上采样后输出恒为 2× 目标（480×864 → 960×1728）。

**修正**（commit 见下）：`inject.width/height` 仅保留 `320.290` 的 `resize_type.width/height`，`320.295` 的 width/height 恢复走模板 `a/2` 链接。离线构建图验证：

```
320.290 -> {"resize_type.width": 480, "resize_type.height": 864, ...}
320.295 -> {"width": ["320.292", 1], "height": ["320.294", 1], "length": 76, ...}
```

回归：`pytest -q` → **31 passed**。gateway 为每请求 `load_registry`，改 yaml 即生效，无需重启。

## 720p 卡死分析（第三条冒烟）

- 提交后 running 至 ~1191 s 期间：GPU util 持续 0%（6 采样×5 s），显存 7511/8192 MiB 被占，全机 CPU 20 s 窗口内无进程消耗 >1 s（空闲）。
- ComfyUI HTTP 全死：`/system_stats`、`/queue`、`/history/{prompt_id}` 均 15–30 s 超时（此前正常应答）。prompt_id `c84e3cbd-b5e9-4fc9-8fb8-31e144150f59`。
- 网关侧 `timeout_s: 1800` 于 1811 s 正确触发，任务置 `failed: timeout`——网关超时兜底行为符合设计。
- **推论（高置信）**：修正前 720p 的实际产物分辨率是 1472×2624（目标 736×1312 的 2 倍），8GB 显存上两段全分辨率 + ×2 上采样触发显存/主机内存抖动，ComfyUI 执行线程与 HTTP 线程一起挂死。待 ComfyUI 重启后按修正后 registry 复跑验证（预计不再复现）。

## prompt 注入修复（评审发现）

**Bug**：registry.yaml 原写 `prompt: [{node: "320.319", field: "text"}]`，但模板节点 `320.319`（PrimitiveStringMultiline）唯一的输入键是 `value`。ComfyUI 对未知输入名**静默丢弃**，注入不生效——修复前所有视频（含上文 3 条 PASS 冒烟）实际用的都是模板硬编码提示词 "Egyptian royal..."，用户提示词被丢弃；尺寸/时长结论不受影响，但画面内容与提交词无关（修复前后同请求产物体积 601KB → 1020KB，佐证内容确实变了）。同类问题：`length` 第二注入点 `{320.305, field: "length"}`，实际字段名 `frames_number`（原为无害空转）。

**模板链路核查**（workflows/ltx-2.3-i2v.json）：`320.319(value)` → `320.327 ComfySwitchNode`（switch←320.328=false → 取 on_false）→ `320.303 CLIPTextEncode.text` → 条件。节点选对了，只是字段名错。

**修复**（仅 registry.yaml）：`prompt → [{320.319, value}]`；`length → [{320.295, length}, {320.305, frames_number}]`（保留第二点使音频帧数显式跟随注入值，不再依赖 320.323 的 a*b+1 偶然同值）。

**离线证明 + 回归守卫**：tests/test_templating.py 新增 `test_prompt_inject_reaches_template_node`——加载真实 registry.yaml 与真实模板 JSON，断言标记串 `UNIQUE_MARKER_7f3a` 落入 `320.319.inputs.value`、`76` 落入 `320.305.inputs.frames_number`；并泛化断言**每个模型全部注入点的 node+field 在模板中真实存在**（正是本 bug 类：字段名写错 = 静默无效）。`pytest -q` → **32 passed**。

## MiniMax-H3 探测结论（Task 9）

日期：2026-11-08　分支：feat/v1

**探测方式**：Task 5 真机 `/prompt` 逐节点校验（26 节点模板结构通过，缺文件在校验阶段即定位）+ 本机模型目录文件核对（未启动生成，探测结果由文件缺失直接决定）。

**结论**：`minimax-h3-local` 维持 `available: false`。

**原因（缺 UNET 文件）**：
- 模板 `105.6`(UNETLoader) 要求 `minimax_h3_fl2va_pruned_int8_convrot.safetensors`，本机所有 `diffusion_models` 目录为 0 文件。
- 本机仅有用户已下载的 `qwen3vl_32b_heretic_minimax_h3_nvfp4.safetensors`（heretic 发行版），与模板所需发行版不匹配（模板 CLIP 侧要求 `qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors`，名称亦不同）。
- 其余待补齐文件：VAE `minimax_h3_video_vae_int8_convrot.safetensors`、`minimax_h3_audio_vae_fp32.safetensors`，LoRA `minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors`。

**附加风险**：nvfp4 量化在本机 Ampere 架构（RTX A2000 8GB）上的支持存疑（nvfp4 官方面向 Blackwell+），即使补齐文件也可能不可用或需回退量化方案。

**注入点回填**（本次同时完成，仅数据修正）：转换后模板没有独立 PrimitiveStringMultiline，提示词直挂在 `105.104`(MiniMaxH3ImageToVideo) 的 `prompt` 字段；图像注入 `114`(LoadImage).`image` 不变。已写入 `registry.yaml` 并由 `test_registry.py` 守卫。

**恢复路径**：下载对应发行版的 UNET/CLIP/VAE/LoRA 文件 → 在 ComfyUI 桌面版手动跑通该模板（确认 nvfp4 在本卡可用）→ `registry.yaml` 置 `available: true` 并跑 minimax 冒烟。

### 异常与注意事项

- **系统代理拦截回环流量**：httpx 默认信任 Windows 注册表代理（本机 127.0.0.1:10809），localhost 请求被代理转发出过一次 `ReadError`。验收时两个服务以 `NO_PROXY=127.0.0.1,localhost` 启动、脚本 httpx `trust_env=False` 后全程稳定。运维建议：`start.bat` / 服务化时固定设置 NO_PROXY。
- 短剧 `finalize_polled` 写 artifact `meta`/`result` 的 provider 是字面量 `"ark"`（Ark 轮询收尾通用路径），真实 provider 记录在 ModelCallLog（ark_local）——功能无影响，属短剧侧后续可微调的展示细节。
